# triage-loop

This is a user-invoked intake entrypoint for work that arrived as a raw report. It is separate from `repair-loop`: triage decides what the report is and whether it is ready; repair diagnoses a confirmed failure.

## Canonical roles

Every item carries exactly one category and one state:

- Category: `bug` or `enhancement`.
- State: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`.

Do not use “ready” without one of these exact states. If category or state conflicts, stop and ask the maintainer.

## Process

1. Read the full report, comments, linked evidence, and relevant project glossary. Facts the repository can reveal are the agent's job; do not ask the user for those facts.
2. Set one category and one state. For missing reproduction, expected behavior, scope, or ownership, use `needs-info` and ask the current frontier questions.
3. When the item is ready, write a brief with the user-visible problem, expected behavior, acceptance criteria, non-goals, evidence, dependencies, and `blocked_by` edges. Keep implementation choices out of the brief unless the user already decided them.
4. Apply the configured local record or issue-tracker label only after the user confirms the classification. If an external comment is written, begin it with `> This was generated by AI during triage.`
5. Stop. A `ready-for-agent` item is an input to a later explicit workflow, not an implementation command.

## Output contract

Return category, state, evidence, missing information, acceptance criteria, non-goals, blockers, and the next user action. Preserve the raw report and link every inference to its source.

## Hard stops

- Do not invoke `ddd-core`, `repair-loop`, `adapter-kit`, or `delivery-loop` automatically.
- Do not fix, redesign, or expand the report while triaging it.
- Do not mark an item `ready-for-agent` when a domain decision, reproduction, acceptance criterion, or blocker is still unknown.
